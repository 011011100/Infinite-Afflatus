# 版本升级数据回归

`Data upgrade safety` 使用 GitHub 托管的 Linux、Windows、macOS 临时运行环境，在每次 push、PR 和手动触发时检查当前存储代码是否保留历史数据。与 `Project checks` 独立显示；任一断言失败会使对应系统的检查失败，不自动忽略错误。工作流只有仓库读取权限，不使用业务密钥、真实项目或云端生成 API。

## 测试如何模拟升级

1. 从完整 Git 历史导出固定提交的 `src/main`、`src/shared` 和 `package.json`，放入系统临时目录。旧代码不从当前工作区导入业务模块。
2. 启动独立 Node 进程，调用旧版本真实存储服务创建应用数据库、三个项目及合成素材文件，记录旧版本读取出的数据作为比较依据。旧进程关闭所有数据库后退出。
3. 当前版本打开同一批文件，核对旧数据，再编辑项目名称、卡片位置、文本和设置。另一个项目必须完全保持独立。
4. 关闭当前存储服务，再启动两个独立 Node 进程，分别核对编辑结果、历史数据和源文件内容，防止只验证内存状态或只验证首次打开。
5. 检查 SQLite 完整性和外键；临时数据在测试结束后清理。工作流保留 14 天测试日志，日志包含基线提交、系统、运行时和失败差异，不上传用户数据库。

旧版本与当前版本目前都使用 Node 24.14.0 的 SQLite，以及当前安装的 `tsx` 作为 TypeScript 加载器。历史存储模块的运行依赖只有 Node 内置模块，不安装历史 Electron，也不替换本机正在运行的软件。

## 固定历史基线

基线清单在 `tests/upgrade/baselines.json`。目前没有正式发布安装包，这里固定的是已有历史提交：

| 基线 | 固定提交 | 主要验证内容 |
| --- | --- | --- |
| legacy-draft | `c5ad575ba7dad4dc27540192e74bc4b33228954f` | 项目级生成草稿转换为镜头素材画布；旧快捷键升级 |
| material-workspace | `e0c58b3033e0bd4973d2da5797cb7247a8b962bc` | 多镜头、多组参数、文本顺序与覆盖文本、素材引用、标签和卡片尺寸 |

共同验证项目 ID、名称、原保存目录、画布视口和坐标、组合播放顺序、片段入出点、中文与 emoji、已保存任务，以及升级前已经下载但尚未保存的结果。全部源素材按 SHA-256 和大小核对，文本编辑不得改写源文本文件。目录中用户自己放入的文件必须保留。

额外故障用例包括：不支持的应用／项目数据库版本拒绝打开且数据库字节不变；表结构无法识别时不重新建空库；当前事务内删除记录后强制退出进程，下次打开恢复已提交的数据。另有故意删除记录、改写源文件的对照用例，确认检查确实能识别这些损失。

## 本地运行与失败处理

```bash
pnpm test:upgrade
```

测试不启动 `pnpm dev`，不调用媒体播放器或 FFmpeg；媒体内容为明确标注的合成字节，只验证存储，不验证解码。浅克隆缺少指定提交时，补全 Git 历史再运行，不能退回当前版本生成数据。

失败时先看 GitHub 对应系统的 `Test historical data against current code` 日志或 `data-upgrade-<系统>` 附件。核对数据路径、读取兼容、字段转换和写回逻辑，不通过移除基线、删除断言或重置数据库让测试通过。

## 发布时如何维护

- 现有基线是长期兼容承诺，保留旧 SHA 和旧场景。不能将其改成 `HEAD`、移动分支或每次用新版本重建期望值。
- 发布新的数据格式或重要持久化功能后，追加完整提交 SHA、名称和对应 `scenario`。场景写入器保留既有场景，需要时新增分支或单独写入器，加入新字段的代表数据与断言。不要只换基线却不写入新增功能的数据。
- 修改表结构或 JSON 格式时，先写出旧数据到新格式的升级逻辑，再通过所有历史基线。升级前备份和事务回滚仍是应用功能，不能用测试代替。
- 如需禁止未通过检查的 PR 合并，可在仓库分支规则中要求三个 `Data upgrade (...)` 检查通过。本次只增加工作流，不修改仓库分支规则；检查失败不会撤回已经发生的 push。

## 验证边界

当前两个历史基线的 SQLite 表版本都是 1。测试覆盖真实历史 JSON 格式变化及存储兼容；未来表版本升级时会继续检查旧库是否能打开和保留数据，但当前不声称已经实现 `1 → 2` 的数据库结构迁移、升级前备份或恢复界面。

这些结果证明相应操作系统下的存储业务层读写与进程重启行为。Electron 的 `userData` 路径选择、安装器覆盖／卸载、打包资源、桌面 IPC、真实媒体播放及云端 API 不在此测试范围内。正式打包后还需要独立的“安装旧版 → 创建项目 → 覆盖安装新版 → 启动核对”测试，特别验证应用名称、安装路径和用户数据目录没有意外改变。
