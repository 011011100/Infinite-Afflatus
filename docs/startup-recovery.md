# 启动失败保护与原位置重试

更新时间：2026-10-05。

## 恢复入口

启动时原项目保存盘离线、目录不可读写，或 `userData/app.sqlite` 无法安全打开，应用会保留原生恢复对话框，显示错误、应用数据库位置及能够可靠读取到的原项目目录。

- “重试”按原来的应用数据位置和项目根目录重新打开。连接原磁盘、恢复权限或放回可靠的原数据库后，不必重新启动整个应用。
- “重新定位原项目目录”只在旧目录确实不存在、原应用资料与恢复标记稳定且可核实时出现。同盘改名或移动后，选择实际原目录，预览前后位置、项目及待保存任务，再明确确认。确认默认取消，选错或取消留在原故障提示。
- “查看应用数据位置”仅打开该文件夹；“查看原项目位置”只在原目录已经通过只读应用库校验时提供。位置不存在时打开最近的可用父目录，不创建缺失目录。
- “退出”结束启动；Esc 使用同一退出动作。
- “检查本机备份”读取事先在设置中创建的应用索引与设置备份，先核对时间、原目录和恢复范围，再明确确认。取消检查或确认不会替换资料；详见 [应用索引与设置备份](application-backups.md)。

查看位置不触发数据库重新初始化或重新打开。明确点击“重试”、完成目录重新定位或备份恢复后才开始下一次串行打开；成功后才注册原有业务 IPC、恢复任务并打开首页。此入口不自动更换根目录、新建替代库或删除数据。备份恢复在打开项目库之前执行，原数据库及旁路文件另存保留，并隔离过期任务授权。

## 原目录重新定位

只接收与独立恢复标记中设备、文件身份及创建时间一致的原目录，并检查应用索引中的每个项目目录、项目 ID、数据库结构、完整性和内容证据。相同名称、相同内容的复制目录、符号链接、跨盘复制、新目录身份、仍存在的旧路径及未完成的目录迁移均拒绝。不承诺外接盘重新挂载后身份一定保持。带有旧绝对路径授权的未结束项目包／素材修复操作也拒绝重新定位，不能改写路径后重放原清理。

预览只读，不扫描全部媒体、不解析独立草稿。已有缺失素材或损坏草稿由重新打开后的现有检查处理，不阻止核实真实原目录。确认前再次核对预览的目录、应用库、项目库与代际；预览失效、记录变化或新文件出现时保留全部文件并拒绝提交。

确认时通过 SQLite 一致快照生成候选应用数据库，仅更新根目录与恢复代际，保留其余原始设置、项目和保存任务（含记录顺序）。原 `app.sqlite` 留在 `app-root-relocation-retained/<本次标识>/app.sqlite`；项目目录、素材、独立草稿及完整暂存结果均不搬运或重写。重新打开后才运行原有保存队列：已完整收到的待保存任务正常继续，已保存但目标缺失的最后暂存副本仍保留。此流程不等同于应用备份恢复，不会归档掉原保存队列。

独立 v1 意图 `app-root-relocation.json` 固定原库、候选库、目录、项目证据及前后代际。下一次启动在读取根目录和启动任何任务之前，按实际文件状态续接原库归档、候选发布、标记切换及本次收尾。意外新库、原位置重新出现、身份或内容变化会停止续接并保留资料；不覆盖新文件，也不删除项目。目录重定位与应用备份恢复不能同时进行。

启动期间退出会使尚未确认的选择失效，不等待用户继续操作原生选择框；已经接受的数据库提交及正在打开的库先安全结束，再退出。运行中编辑失联仍沿用保留输入与原位置重试，不提供强制关闭或未保存输入迁移。

## 已有应用数据库的边界

已有 `app.sqlite` 先以只读方式检查版本、固定三表及其字段／唯一约束、SQLite 完整性、必需的绝对 `root` 路径、设置 JSON、项目索引和保存队列。空文件、缺表、缺少根目录、非法 JSON、不支持的新版本或结构不能触发 `CREATE TABLE IF NOT EXISTS` 或补默认目录。

进入可写连接时使用 SQLite `mode=rw`，禁止在文件被移走后创建空库；应用数据库文件必须是普通文件，连接前后的文件身份必须保持一致，并在任何可写 PRAGMA 之前重新校验实际连接。构造期间任何失败都会关闭已经取得的数据库连接。新库的初始化建表和初始根目录写入在事务中完成；中断产生的已有空／不完整文件仍按故障处理，不自动删除并重来。

已记录的项目目录必须真实存在且可写。应用使用自己独占创建的随机小文件检查实际写入能力，再按文件身份清理该检查文件，不覆盖已有文件、不递归清理。目录离线或只读时不先改写根目录，也不会启动保存队列把待保存结果写到其他位置。恢复原路径后，已有的项目 ID、队列和迁移日志继续沿用；迁移已经切换的库不会自动回退到旧副本。

## 应用数据库缺失时

仅首次安装且没有已知管理数据痕迹时才创建新库。当前痕迹包括 SQLite 的 journal／WAL／SHM 旁路文件、独立的 `app-backup-anchor.json`／`app-backup-restore.json`／`app-root-relocation.json`、非空的 `app-backups`、`app-backup-retained`、`app-root-relocation-retained`、`staging`、`export-work`、`preview-work`、`asset-recovery`、`workspace-drafts`、`project-edit-drafts`、`drafts`、`recovery-drafts`、包操作临时目录，以及默认项目根目录内已有的受管项目数据库。

空的预建工作目录和 Electron 自己的 Preferences 等配置不等同于已保存项目。发现管理痕迹时保留全部文件，要求放回原应用数据库，不尝试扫描目录自动重建保存队列或迁移日志。扩展新的独立持久化目录时，需要把目录加入 `MANAGED_DATA_DIRECTORIES`。

独立恢复标记记录应用资料与原项目目录的身份；原数据库缺失时，该标记本身也会阻止创建空库。若数据库、恢复标记及所有已知痕迹都被外部删除，且旧项目位于无法获知的自定义位置，仍不能可靠找回该位置。首次安装判断不会全盘搜索或自动找回所有丢失的库。

## 验证

`tests/startup-recovery.test.ts` 使用独立目录和真实 SQLite 覆盖空库、损坏文件、较新版本、缺表／缺 root／错误结构、非法 JSON、较新版本 WAL 库拒绝、预检后文件移走或替换链接、构造失败关闭、管理痕迹检测、只读目录、离线原目录恢复后队列继续保存，以及原生对话框的串行重试控制。被拒绝的现有文件保持字节和修改时间，默认库不会被创建。

`pnpm test:upgrade` 继续使用既有固定提交历史基线，不更新旧期望或格式版本；各批验证结果见 [商业可用性推进清单](commercial-readiness.md)。已有应用库只丢失最近项目索引时，仍可从项目文件夹重建列表，并保留应用设置和原保存队列；这与丢失整个应用数据库后自动新建不是同一种操作。

`tests/browser/startup-recovery.cjs` 在构建后的 macOS 生产主进程／preload 中验证了三个场景：原项目目录失联后重试，损坏应用库拒开，以及空应用库拒开。目录放回后实际 IPC 读回原项目、视口和失败保存队列，暂存原文件保留；拒绝时未开主窗口、未创建替代目录且应用数据库字节／修改时间不变。此证据不代表 Windows 或正式安装包验证。

`tests/browser/root-relocation.mjs` 通过七次隔离生产启动覆盖原目录真实改名、选择取消、确认取消、复制目录拒绝、选择框未结束时退出、确认定位与两次独立重开。核对原库归档、原项目和草稿字节、保存队列及完整暂存副本；具体平台与完成结果见[商业可用性推进清单](commercial-readiness.md)。

启动保护现支持原位置重试、同盘原目录重新定位与受验证的本机应用索引备份恢复。数据库自动修复、未知目录身份认领或只读项目浏览模式仍未实现。
